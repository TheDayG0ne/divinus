# OpenWall settings

`/api/openwall` is a settings-only endpoint. **No sender, scheduler, or upload is implemented.** POST with `enabled=1` returns 409 with an explicit error and does not change the settings. An existing file with `enabled=1` fails closed on GET (500); POST with `enabled=0` can replace it.

The device must be claimed and requests must authenticate as root using HTTP Basic and the shadow password. Cross-site requests are rejected. GET returns JSON with `enabled` (boolean), `interval` (minutes), `caption`, and `camera` (index). Defaults are false, 60, empty, and 0. Query strings are rejected. Only GET and POST are supported; other methods return 405 with `Allow: GET, POST`.

POST replaces all settings using `application/x-www-form-urlencoded` and requires the non-simple header `X-OpenWall-Request: 1` as CSRF protection. Fields are `enabled` (only 0 is currently accepted), `interval` (15, 30, 60 or 120 minutes), `caption` (valid UTF-8, at most 128 bytes, no controls), and `camera` (currently only 0, the local pipeline). Duplicate, missing and unknown fields are rejected. Content-Length must contain only decimal digits and match the body, which is limited to 1024 bytes; transfer encoding is rejected. A successful POST returns the new JSON. Clients must use the same origin; no CORS access is provided.

Settings are stored in `/etc/openwall.conf`, atomically replaced with a root-owned mode 0600 file. The file is synced before rename and its parent directory is synced afterward; success is reported only if both syncs succeed. Durability depends on filesystem and storage guarantees. A failure after rename returns 500 but the new file may already be visible (and may survive a restart); it is not rolled back. An invalid, unsafe or unreadable existing file fails closed rather than silently resetting settings.

The server speaks native HTTP only; it does not provide HTTPS. Its `Origin`/`Referer` check accepts only `http://` and rejects an `https://` origin, so putting it behind a TLS reverse proxy is not a supported working configuration. HTTP Basic credentials and the request contents are sent without encryption. Restrict access at the network layer, for example with network isolation or a VPN; this documentation does not promise secure HTTP transport.
